# Отчёт об интеграции ML и проверке MVP FlowStaff AI

Дата: **17 октября 2026 года**.

## Результат

Новые файлы из `attrition-ml-service` подключены к существующему проекту. ML остаётся отдельным микросервисом. Подтверждён сквозной сценарий: приём данных → обучение новой модели → ручная активация → прогноз через действующий Java API → сохранение прогноза → отображение в существующей системе.

**MVP пригоден для демонстрации проверенных сценариев.** Техническая работоспособность модели подтверждена на синтетических данных; качество прогнозирования реальных увольнений пока не подтверждено. Новый цикл управления моделями работает через внутренний API. Действующая кнопка обучения в интерфейсе сохраняет прежний процесс V1.

## Что исправлено при подключении файлов

Предоставленная версия меняла запуск на порт 8000, API на другие адреса и форматы, а хранение по умолчанию — на SQLite. Java и Compose ожидали порт 8082, `X-Service-Token`, MySQL и прежние JSON-контракты. Простая замена файлов нарушала совместимость.

Выполнено:

1. Восстановлен действующий запуск `python -m app.server`, порт 8082, профили и проверки готовности. V1 сохранён; V2 смонтирован в `/internal/v2` того же сервиса.
2. Настройки V2 читают существующие переменные MySQL, токен, часовой пояс и путь общего тома моделей. Без настроенного токена закрытые операции недоступны.
3. Добавлена Liquibase-миграция `ml-006-v2-ml-workflow`. Новые таблицы `ml_v2_*` находятся в `enterprise_ml`. Автоматический `create_all` разрешён только для локального SQLite; в MySQL таблицами управляют миграции.
4. Добавлена синхронизация операционных снимков из действующего ML-хранилища. Учитываются естественный ключ сотрудник/дата/схема и повторная отправка с другим идентификатором.
5. Одобренная V2-модель публикуется в `ml_model_versions`. Адаптер возвращает Java прежние поля `modelVersionId`, `riskLevel`, `topFactors` и остальные ожидаемые данные. Реестры обновляются одной MySQL-транзакцией.
6. Сохранены четыре уровня риска. В MySQL оба контура используют существующую таблицу порогов: по умолчанию 0,30 / 0,60 / 0,80.
7. Подключены авторазметка, защита размеченных операционных снимков, CSV-импорт, групповое разбиение, метрики, проверка качества кандидатов, контрольная сумма модели и копия датасета.
8. Исправлено сравнение моделей: при повторном обучении сохраняется контрольная группа сотрудников активной V2-модели. Это исключает сравнение старой модели на сотрудниках из её обучающей части. Для ранних артефактов без сохранённой группы сравнительная проверка пропускается; абсолютные пороги качества сохраняются.
9. Добавлены проверки отрицательных/бесконечных чисел, идентификаторов, полноты нагрузки, будущих дат и параметров истории. Повреждённый кандидат не заменяет активную модель.
10. Зафиксированы версии основных Python-зависимостей, восстановлен Docker-контекст сборки, добавлены тесты совместимости, отдельный тестовый Compose и инструкции.

## Ограничения и доработки для MVP

### 1. Единый интерфейс нового обучения — высокий приоритет

Новый цикл V2 работает через служебный API. Текущая кнопка обучения вызывает старый V1-процесс с прежними правилами и автоматической публикацией. Новый CSV имеет другую схему. Оба пути сохранены ради совместимости, но требуют разъяснения пользователю.

**Предложение:** добавить в существующее администрирование небольшую страницу «Кандидаты модели»: запустить обучение V2, показать метрики/причины отказа, активировать одобренную версию. Java должна выполнять служебные запросы и записывать пользовательское действие в аудит. После перехода интерфейса старый путь можно постепенно вывести из употребления.

**Зачем:** проверка качества станет частью обычного рабочего сценария, уменьшится риск случайной перезаписи активной модели старой кнопкой. Текущий фронтенд и сервисную архитектуру можно использовать дальше.

### 2. Полнота истории признаков — высокий приоритет

Новый ML различает `null` и фактический ноль и принимает число дней доступной нагрузки. Существующий Java `FeatureBuilder.scale()` превращает отсутствующее число в 0, а текущий контракт не передаёт новые показатели полноты. Синхронизация старых снимков не может восстановить утраченное различие.

**Предложение:** расширить контракт сбора признаков двумя счётчиками дней, сохранять неизвестную нагрузку как `null`, зафиксировать исторические значения на дату снимка.

**Зачем:** модель перестанет трактовать отсутствие наблюдений как отсутствие работы. Это влияет на достоверность сильнее, чем замена алгоритма классификации.

### 3. Передача кадровых событий и расписание — высокий приоритет

V2 принимает категории увольнений и умеет размечать снимки. Автоматическая отправка этих событий из Java и ежедневный запуск синхронизации/разметки ещё не подключены. Имеющиеся поля даты и причины увольнения сами по себе не образуют интеграцию. Изменение уже обработанного факта увольнения автоматически не пересматривает прежние метки.

**Предложение:** хранить структурированную категорию причины, отправлять события с повторяемым идентификатором; добавить ежедневный сбор/разметку через существующий Java-планировщик. Для исправлений кадровых событий предусмотреть ограниченный пересмотр затронутых меток с аудитом.

**Зачем:** будет постепенно накапливаться реальный обучающий набор. Класс 0 появляется только после полного окна наблюдения; при горизонте 90 дней это нельзя заменить немедленной генерацией нулей.

### 4. Реальная оценка и калибровка — до практического применения процентов

Сейчас проверена техника на синтетике. `class_weight="balanced"` помогает обучению на редком событии, но проценты могут плохо соответствовать фактической частоте увольнений. Групповая проверка не заменяет временную проверку на более поздних событиях.

**Предложение:** после накопления истории провести временной бэктест, калибровку вероятностей и оценить precision/recall в пределах числа сотрудников, которых HR реально может сопровождать. Проверить качество по подразделениям при достаточном числе примеров.

**Зачем:** отличить технически корректный расчёт от полезного кадрового сигнала и подобрать обоснованные пороги. Пока проценты и уровни подходят для демонстрации механизма; пригодность для реальных решений требует данных.

### 5. Упростить сопровождение двух ML-контуров — средний приоритет

V1 и V2 временно имеют разные таблицы и форматы артефактов. Это сохраняет работающие возможности, но создаёт дополнительную поддержку. Блокировка обучения V2 действует в одном процессе; многопроцессный запуск или несколько ML-реплик пока не рассчитаны на одновременную публикацию.

**Предложение:** для текущего MVP оставить один ML-процесс, использовать единый интерфейс администрирования, описать переключение версии и восстановление. После перехода UI объединить внутренний жизненный цикл. Фоновую очередь обучения вводить при реальном росте длительности операций.

**Зачем:** меньше изменений одновременно, проще воспроизводить ошибки и откатывать модель. Текущий масштаб не требует дополнительной инфраструктуры для выполнения проверенных сценариев.

### 6. Сохранить воспроизводимую приёмку — средний приоритет

В существующем `verify-stage2.py` обнаружено устаревшее ожидание: после создания сотрудника тест ждал общий список, а приложение корректно открывает карточку `/employees/{id}?created`. Исправлено ожидание теста.

**Предложение:** запускать Java- и ML-тесты при каждом изменении; сквозную приёмку выполнять на отдельном стенде. Расширять её сценариями изменения задач, отказа workload-сервиса и восстановления резервной копии при изменении соответствующих функций.

**Зачем:** проверять сохранение MVP по наблюдаемому поведению, включая отрицательные сценарии. Полный restore drill, production TLS, нагрузочное тестирование и ручной обход всех действий интерфейса в рамках этой проверки заново не выполнялись.

### 7. Небольшие улучшения интерфейса — средний приоритет

На desktop главная показывает шесть KPI в сетке, где последняя карточка переносится в отдельную строку с большим свободным местом. На мобильной странице прогнозов развёрнутые фильтры занимают почти весь первый экран.

**Предложение:** согласовать сетку KPI с числом карточек, например 3×2 на подходящей ширине; на mobile сворачивать дополнительные фильтры и показывать число активных условий.

**Зачем:** пользователю будет проще увидеть ключевые показатели и быстрее добраться до прогнозов. Для этого достаточно существующих шаблонов и CSS дизайн-системы.

## Приёмка административного CRUD

Расширенная проверка `tools/verify-stage2.py` завершена успешно на изолированной тестовой базе. Подтверждены:

- CRUD подразделений; запрет циклической иерархии, дубликатов и удаления используемой записи; конфликт устаревшей версии при редактировании.
- Создание сотрудника с выбранными подразделением, должностью и графиком; открытие его карточки после сохранения.
- Изменение должностей и графиков, ограничения архивных записей, календарные исключения и их фактическое влияние на доступные рабочие часы.
- Создание и связь пользователя с сотрудником, смена ролей, блокировка/разблокировка, сброс пароля, архивирование и отзыв действующих сессий.
- Защита последнего администратора, запрет административных действий сотруднику, отклонение POST без CSRF.
- Удаление неиспользуемых справочников и сохранение настроек организации.

## Практический следующий шаг

Сначала подключить новый цикл к существующему администрированию и обеспечить отправку достоверных кадровых событий/снимков. Затем накопить историю и проверить качество на ней. Это делает уже работающий MVP более полезным без полной переработки фронтенда или развёртывания дополнительных сервисов.

Порядок вызова нового API и команды запуска приведены в [README ML-сервиса](../attrition-ml-service/README.md).
