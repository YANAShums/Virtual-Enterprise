# Отчёт о семи доработках FlowStaff AI

Все семь этапов реализованы и приняты. После каждого этапа выполнялась проверка его критериев и отдельный коммит. План и журнал: [mvp-improvement-plan.md](mvp-improvement-plan.md). Изменения проверялись на изолированном стенде `flowstaff-ml-check` с отдельными базами и демонстрационными данными.

## Что подтверждено проверками

- Полный Java-набор: **107 тестов**, без падений. После изменения шаблонов дополнительно прошли **11 тестов рендеринга страниц**.
- Итоговый ML-набор: **69 тестов**, без падений. Покрыты разметка, исправления событий, независимость групп обучения/калибровки/проверки, сериализация, гейт, совместимость и освобождение блокировки после сбоя.
- Сквозная интеграция: **25 проверок ML/Java**, затем проверки администрирования, признаков, кадровых событий, качества, общего жизненного цикла и отката.
- Задачи: создание, ошибки ввода, CSRF, переходы `PLANNED → IN_PROGRESS → REVIEW → DONE`, запрет недопустимого перехода и устаревшей версии, отображение в Kanban.
- Отказы: workload возвращает контролируемый 503, страницы доступны, задача без расчёта не создаётся; после запуска расчёт восстанавливается. При отказе ML возвращается сохранённый прогноз с признаком устаревания; кадровые события остаются в очереди.
- Административный CRUD: подразделения, должности, графики, календарь, пользователи, роли, блокировка/сброс пароля, отзыв сессий, защита последнего администратора и связанные ограничения.
- Restore: три базы восстановлены во временную MySQL; совпали девять счётчиков записей. Проверены контрольные суммы комплекта и всех V2-артефактов, включая подпапки. В первом запуске тест сверял таблицу прогнозов в неверной базе; ошибка теста исправлена, восстановление отдельно повторено успешно.
- Браузер: **1440×900, 1280×720, 390×844**, роли ADMIN и PROJECT_MANAGER. Применение/сброс фильтров, сохранение значений, сворачивание, фокус, reduced-motion; без горизонтального переполнения и ошибок JavaScript. Скриншоты просмотрены, ошибка окрашивания карточек легендой исправлена.

Логи: `output/improvement-stage*-*.log`. Сквозные результаты и скриншоты: `output/ml-acceptance`, `output/playwright/ml-acceptance`. Результат restore: `output/improvement-stage6-restore.json`; браузера: `output/improvement-stage7-results.json`. Эти файлы создаются локально и не включаются в Git.

## Что остаётся ограничением MVP

**Реальная точность прогноза пока не подтверждена.** Синтетика проверяет технический механизм. Для кадровых решений нужны достоверные исторические снимки, проверенные категории увольнений, независимый поздний период и согласование допустимого числа сигналов с HR. Даже `REAL_HISTORY` в CSV является заявлением источника. Поэтому интерфейс показывает `NOT_VALIDATED`, а при недостатке поздней истории — `INSUFFICIENT_DATA`. Пороги риска 0,30/0,60/0,80 сохранены.

Нагрузка — сохранённая оценка по текущему плану задач на момент наблюдения, а не табель фактически отработанных часов. Прошлые наблюдения не достраиваются из сегодняшнего плана. Это защищает историю признаков, но для точного учёта фактических часов потребуется отдельный источник.

Проверенное восстановление охватывает базы и файлы моделей. Пользовательские вложения в файловом хранилище этим комплектом не резервируются; для восстановления всего файлового содержимого нужно дополнить backup соответствующим томом. Согласованная копия нескольких баз и моделей требует остановки записей либо отдельного механизма координации — в приёмке записи останавливались.

Основной режим MVP — один ML-процесс. Межпроцессная блокировка MySQL защищает операции публикации, но полноценная эксплуатация нескольких реплик требует отдельной проверки общих файлов и кешей. Очередь обучения и дополнительная инфраструктура пока не нужны для проверенного масштаба. Workflow GitHub Actions подготовлен; запускался локальный сценарий, а не удалённый workflow.
