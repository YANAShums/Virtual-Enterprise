# Развёртывание FlowStaff AI

Актуальная постановка: «FlowStaff_AI_Техническое_задание_v2.1.docx», этап 1.
Это инструкция инфраструктурного этапа, а не подтверждение готовности всего приложения к публичной эксплуатации.

## Локальная разработка

```powershell
Copy-Item .env.example .env  # только если локального .env ещё нет
docker compose up -d --build --wait --wait-timeout 180
python tools/verify-stage1.py
```

HTTP приложения доступен только на localhost:8080, MySQL — localhost:3307.
Workload и ML не публикуют порты на хост. Compose использует локальный профиль `docker`;
базовый application.yml содержит только демонстрационные значения. Не использовать их в эксплуатации.
Скрипт приёмки временно останавливает только ML, затем восстанавливает его в finally.
`SMOKE_USERNAME` и `SMOKE_PASSWORD` позволяют проверить вход, если локальный администратор переименован.

## Production-профили и TLS

Java: `SPRING_PROFILES_ACTIVE=prod`; ML: `ML_PROFILE=prod`.
Java-сервисы читают PEM-сертификат и PKCS#8-ключ из `TLS_CERTIFICATE` и `TLS_PRIVATE_KEY`.
ML запускается через `python -m app.server`, проверяет обязательные настройки и включает HTTPS.
При отсутствующих параметрах/файлах запуск завершается ошибкой, отката на HTTP нет.
Демонстрационные пароли БД и сервисные токены запрещены production-проверками.
Enterprise требует HTTPS для `WORKLOAD_SERVICE_URL` и `ML_SERVICE_URL`.
ML URL пока является подготовленной настройкой: бизнес-интеграция прогнозов относится к этапу 11.

У Java health доступен на HTTP 127.0.0.1:8083 **внутри контейнера**; этот порт нельзя публиковать.
ML readiness использует HTTPS с проверкой CA и имени сервера, а также service token.
Сессионная cookie Enterprise в prod имеет Secure, HttpOnly и SameSite=Lax.

### Проверка TLS на одном компьютере

`docker-compose.prod.yml` — дополнение к основной конфигурации для проверки production-профилей.
Требуется Docker Compose 2.24.4 или новее. Эта конфигурация не заменяет разнесение по физическим узлам.

1. Скопировать `.env.production.example` в `.env.production`, заполнить уникальные секреты.
2. Указать абсолютный `TLS_DIRECTORY` с файлами:
   - `enterprise.crt`, `enterprise.key` — сертификат входного имени приложения;
   - `workload.crt`, `workload.key` — SAN `workload-service`;
   - `ml.crt`, `ml.key` — SAN `attrition-ml-service`;
   - `ca.crt` — доверенный CA для ML;
   - `truststore.jks` — JKS только с публичными сертификатами доверенных CA для Java-клиента.
3. Выдать процессам право чтения только необходимых файлов; ключи монтируются отдельно и read-only.
   Пользователю `appuser` в ML-контейнере нужен доступ к его ключу. Не класть ключи в образ.
4. Запустить:

```powershell
docker compose --env-file .env.production -f docker-compose.yml -f docker-compose.prod.yml config --quiet
docker compose --env-file .env.production -f docker-compose.yml -f docker-compose.prod.yml up -d --build --wait --wait-timeout 180
```

В этом режиме MySQL не публикует порт; вход приложения — HTTPS localhost:8443.
`HTTPS_BIND_ADDRESS` задаётся явно при необходимости доступа с другого узла.
Корневой сертификат должен быть доверенным для браузера; не отключать проверку TLS.
JKS не содержит приватных ключей; при загрузке JVM без пароля пропускается проверка целостности JKS,
поэтому целостность обеспечивается доверенным источником файла и read-only монтированием.

Не запускать этот режим поверх существующего тома с новыми паролями без ротации учётных записей.
Для испытаний следует использовать отдельный Compose-проект, собственные container_name, порты и тома.
Не переносить демонстрационные учётные записи/seed в публичное окружение: их замена и полный
RBAC/scope входят в последующие этапы. По этой причине данный профиль сам по себе не является
разрешением на публикацию приложения в интернете.

### Три физических узла по ТЗ

- Клиентский узел: браузер, доступ только к HTTPS Enterprise.
- Серверный узел: Enterprise, Workload, core/workload MySQL; внутренние порты закрыты от клиентов.
- Интеллектуальный узел: ML и enterprise_ml MySQL, каталог версий моделей.

Для раздельных узлов использовать те же образы с prod-профилями и отдельными адресами БД:
`CORE_DB_URL`, `WORKLOAD_DB_URL`, `ML_DB_HOST`, `ML_DB_PORT`. URL Workload/ML должны содержать
реальные внутренние DNS-имена, соответствующие SAN сертификатов. На ML-узле Liquibase применяет
`attrition-ml-service/db/changelog.xml` перед стартом сервиса. Разрешить соединение к ML только
с серверного узла; к каждой БД — только от соответствующих сервисов и защищённого администрирования.
Токен не заменяет сетевые правила и TLS. Межузловые соединения MySQL должны быть защищены;
локальный Compose с `useSSL=false` предназначен для закрытой сети на одном хосте.

## Миграции и обновление без потери данных

- На пустом томе init-скрипты создают базы и пользователя; таблицы создаёт Liquibase.
- На существующем томе db-bootstrap добавляет enterprise_ml, ml-migrations применяет baseline.
- Применённые changesets не редактировать; добавлять новые changesets.
- `docker compose up -d --build` сохраняет именованные тома.
- Не использовать `down -v` для обновления или смены пароля. Для ротации сначала выполнить
  контролируемое изменение учётной записи MySQL, затем обновить внешний секрет и перезапустить сервисы.
- Не выводить `.env`, полный `docker compose config` и реквизиты подключения в публичные логи.

активной и предыдущей ML-модели и проверка восстановления реализуются на этапе 14.

резервирования/восстановления и результатами реального испытания восстановления.

Настройки TLS опираются на [Spring Boot SSL](https://spring.io/blog/2023/06/07/securing-spring-boot-applications-with-ssl/)
и [Uvicorn HTTPS](https://www.uvicorn.org/settings/#https).
