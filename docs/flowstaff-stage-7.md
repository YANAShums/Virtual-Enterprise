# Этап 7. Исторические признаки для ML

Реализован детерминированный Feature Builder, который формирует единый набор признаков текучести для каждого активного сотрудника и сохраняет снимки в схеме `enterprise_ml`. Операционный снимок создаётся только на текущую дату предприятия; накопление истории выполняется ежедневным заданием в 02:00 по часовому поясу `Europe/Minsk` (значение настраивается через `ML_FEATURE_TIME_ZONE`).

## Состав набора признаков

| Признак | Правило расчёта |
|---|---|
| `tenure_months` | Полные месяцы между датой найма и датой снимка |
| `employment_rate` | Текущая ставка сотрудника |
| `department_code`, `position_code` | Стабильные коды подразделения и должности |
| `active_projects_count` | Активные участия в проектах на дату снимка |
| `active_tasks_count` | Задачи в статусах `PLANNED`, `IN_PROGRESS`, `REVIEW` на дату снимка |
| `overdue_tasks_30d` | Просроченные задачи с плановым окончанием за последние 30 дней |
| `completed_tasks_90d` | Задачи, фактически завершённые за последние 90 дней |
| `avg_task_delay_days_90d` | Средняя положительная задержка завершённых задач за 90 дней; досрочное завершение даёт 0 |
| `avg_workload_30d`, `avg_workload_90d` | Средняя загрузка по дневным снимкам сервиса нагрузки |
| `overload_days_30d`, `overload_days_90d` | Количество дней с загрузкой выше 100% |
| `absence_days_90d` | Дни согласованных отсутствий в окне 90 дней |
| `task_reassignments_90d` | Изменения назначений задач за 90 дней |
| `project_changes_180d` | Вступления в проекты и выходы из них за 180 дней |

Каждый снимок получает детерминированный UUID из идентификатора сотрудника, даты и версии схемы `attrition-features-v1`. Повторный запуск обновляет ту же запись и не создаёт дубликат. Целевая метка `target_label` остаётся пустой для операционных данных.

## Защита от утечки данных

Все временные окна заканчиваются в конце даты снимка. Отсутствия дополнительно ограничиваются датой создания записи. Дата увольнения, причина увольнения, готовая метка текучести, события после даты снимка и чувствительные признаки не входят в DTO, API и таблицу признаков. ML-сервис отклоняет неизвестные поля и даты из будущего.

Операционный Builder не выполняет задним числом расчёты из текущего состояния: запрос прошедшей или будущей даты получает `400 INVALID_ARGUMENT`. Историческая загрузка подготовленных срезов относится к этапу 8.

## Интеграция и доступ

- `GET /api/v1/attrition/features/{employeeId}` — предварительный просмотр текущего набора для администратора, руководителя предприятия или руководителя того же подразделения.
- `POST /api/v1/attrition/features/rebuild` — пакетная генерация для всех активных сотрудников; доступна администратору и руководителю предприятия.
- `GET /internal/v1/workload/features/{employeeId}` — агрегаты нагрузки за 30 и 90 дней по сервисному токену.
- `POST /internal/v1/features/snapshots` — идемпотентная пакетная запись в ML-сервис по сервисному токену.
- `attrition_feature_snapshots` — таблица снимков со строгими ограничениями, уникальностью сотрудника, даты и источника.

## Результат приёмки

- Java: 67 тестов, ошибок и пропусков нет.
- Python: 20 тестов, ошибок нет.
- Liquibase: применена миграция `ml-002-feature-snapshots`; все три приложения имеют статус `healthy`.
- Browser/API: текущий набор возвращается с кодом 200; прошедшая дата отклоняется с кодом 400; сотрудник получает 403.
- Идемпотентность: первый запуск сохранил 6 снимков, повторный обновил те же 6 записей.
- База ML: 6 записей, 6 уникальных UUID и 6 сотрудников; `target_label` в операционных снимках не заполнен.
