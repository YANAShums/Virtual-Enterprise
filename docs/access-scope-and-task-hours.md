# Области доступа и фактические трудозатраты

Дата: 03.11.2026.

## Выполнено

1. Добавлен `AccessScopeService`: полномочия проверяются относительно конкретного сотрудника, проекта и задачи. Учитываются активные роли; отсутствие связанного профиля не открывает доступ. ADMIN имеет общую область, ENTERPRISE_MANAGER — предприятие, DEPARTMENT_MANAGER — подразделение, PROJECT_MANAGER — проекты с назначением руководителем или активной проектной ролью PROJECT_MANAGER.
2. Области применены к спискам задач, проектов, сотрудников, доске, карточкам, обзору, загрузке, кадровой аналитике и её отчётам. Запрет работает на сервере при прямом запросе, а не только через скрытие кнопки. Агрегаты и тренды кадровой аналитики фильтруются SQL по предприятию и подразделению.
3. Руководитель проекта управляет своими проектами, командой и задачами, выбирает участников проекта, принимает результат. Кадровые риски ему недоступны. Создание проекта доступно администратору и руководителю предприятия.
4. Руководитель подразделения работает с задачами своих сотрудников в доступных проектах. Для назначения допустимы сотрудники его подразделения или действующие участники проекта. Изменять проекты он не может. Расчёт кандидатов учитывает эту область.
5. Сотрудник видит собственные задачи и профиль, может начать работу, передать её на проверку, вернуть завершённую задачу в работу, комментировать и отмечать существующий чек-лист. Принимать результат, менять параметры и исполнителя, добавлять и удалять пункты чек-листа он не может.
6. Наблюдатель читает проекты, где состоит участником, и их задачи; изменения запрещены. На странице загрузки ему предоставляется только сводка по участникам доступных проектов, без персональной таблицы. Кадровая информация закрыта.
7. Старые уведомления и их счётчик повторно проверяются по текущей области: отзыв доступа не оставляет видимые кадровые сообщения о чужих сотрудниках.
8. Для перехода IN_PROGRESS → REVIEW добавлен диалог «Завершить выполнение»: обязательные итоговые часы и необязательный комментарий. Сервер принимает положительное значение с максимум двумя знаками после запятой в пределах DECIMAL(10,2). Превышение плана не блокирует сохранение. Проверяется version; TaskResponse возвращает actualHours. При возврате на доработку часы сохраняются, при повторной передаче заменяются общим итогом. В аудите фиксируются старые и новые часы и статус.

## Проверка

- `mvn clean package`: общая сборка, React и Java-тесты прошли после основных изменений.
- После завершающих изменений: `mvn -pl enterprise-app -am test -Dfrontend.skip=true` — 125 тестов, без ошибок и пропусков; тесты workload-service — 15, успешно в общей проверке.
- Новые проверки охватывают шесть ролей, чужой проект/подразделение, смешанные слабые роли, отсутствие профиля и ролей, назначение, агрегированный просмотр наблюдателя, часы и скрытие старых уведомлений.
- Chromium: реальные учётные записи admin, manager, employee. Сотруднику показаны только 5 из 14 задач; чужая карточка сотрудника, чужая задача, редактирование и кадровая аналитика возвращают 403. Для руководителя проекта проверены запреты кадровой аналитики и создания проекта.
- Проверены обязательность часов, запрет нуля, точность и предел числа, конфликт версии 409, запрет сотруднику принять задачу 403. Диалог допускает 20,50 ч и закрывается Escape. Успешная запись итоговых часов и замена предыдущих проверены сервисными тестами; браузерные отрицательные запросы не меняли рабочие задачи.
- В браузере проверены обзор, задачи, проекты, сотрудники, загрузка, доска, текучесть и отчёты при 1440×900, 1280×720, 390×844: страницы отрисованы, горизонтального переполнения страницы нет.
- Собран и запущен контейнер enterprise-app; база и данные сохранены.

## Использование

В собственной задаче со статусом «В работе» выбрать «Завершить выполнение», ввести итоговое количество часов и нажать «Передать на проверку». После возврата на доработку ввести новый общий итог: например, 11,5 вместо предыдущих 8, а не дополнительные 3,5 часа.

Руководителя проекта определяют поля руководителя и активного участия проекта. Подразделение и предприятие пользователя берутся из связанного профиля сотрудника. Для наблюдателя область просмотра задаётся участием в проекте. Полноценный многопредприятийный административный интерфейс и отдельный журнал рабочих сессий в эту доработку не входят.

Браузерные сценарии и логи этой приёмки находятся в локальной игнорируемой папке `output/access-scope`. Проверки остальных трёх ролей выполнены модульными тестами, а не отдельными реальными браузерными аккаунтами.
