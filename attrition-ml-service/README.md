# ML-модуль FlowStaff AI

ML остаётся отдельным Python/FastAPI-сервисом на порту **8082**. Основное приложение — Spring Boot/Thymeleaf; MySQL и действующие маршруты Java сохранены.

## Два совместимых API

| API | Назначение |
| --- | --- |
| `/internal/v1` | Действующий контракт Java: снимки, CSV-импорт, прежнее обучение, сведения о модели, одиночный и пакетный прогноз |
| `/internal/v2` | Новый цикл: события увольнений, авторазметка, обучение кандидата, проверка качества, ручная активация, история прогнозов |

Все операции требуют `X-Service-Token`, заданный в `ML_SERVICE_TOKEN`. V2 также принимает `X-API-Key` для отдельного локального запуска. Без настроенного токена доступ закрыт. `/health` — открытая проверка жизнеспособности. Документация API не публикуется наружу.

**Кнопка обучения в текущем интерфейсе продолжает использовать прежний v1-процесс.** Новый цикл пока вызывается внутренним API. При активации одобренной v2-модели она публикуется в существующий реестр, поэтому Java и текущие страницы прогнозов используют её без изменения своего контракта.

## Запуск вместе с проектом

Из корня репозитория:

```powershell
docker compose up -d --build
```

Не заменяйте корневой `.env` файлом из этого каталога: локальный пример здесь предназначен для отдельного SQLite-запуска V2. В Compose сервис получает MySQL, служебный токен и пути из существующих настроек проекта. SQLAlchemy не создаёт таблицы в MySQL автоматически: используется Liquibase, включая миграцию `ml-006-v2-ml-workflow`.

V2 хранит данные в таблицах `ml_v2_*` базы `enterprise_ml`. Существующие таблицы и данные V1 остаются на месте. Модели V2 расположены в `/data/models/v2`, зафиксированные датасеты — в `/data/models/datasets`; существующий backup архивирует этот том рекурсивно.

## Новый рабочий цикл

Каждый адрес ниже начинается с `/internal/v2` и требует служебный токен.

1. `POST /snapshots/sync-project?limit=5000` — перенести до 5000 последних операционных снимков из таблицы действующего проекта. Лимит можно увеличить до 50000. Полнота старой истории нагрузки остаётся неизвестной.
2. `POST /snapshots` — принимать новые снимки непосредственно в формате V2.
3. `POST /terminations` — принимать подтверждённые факты увольнений с категорией `VOLUNTARY`, `INVOLUNTARY`, `CONTRACT_END` или `OTHER`.
4. `POST /labeling/run` — разметить операционные снимки. Добровольное увольнение в течение 90 дней даёт класс 1; отсутствие события после полного окна — 0; нецелевые увольнения исключаются.
5. `POST /imports/csv` — альтернативно импортировать размеченную историю. В CSV нужны все столбцы схемы V2; пустое числовое значение сохраняется как пропуск. Незавершённое окно наблюдения отклоняется.
6. `POST /training/run` — обучить модель-кандидат. Минимумы по умолчанию: 30 положительных, 100 отрицательных примеров, 50 сотрудников. Train/test не содержат одних сотрудников. При последующих обновлениях сохраняется проверочная группа активной V2-модели.
7. `GET /models` — проверить метрики и причины отказа. Порог ROC-AUC — 0,65; lift PR-AUC — 1,5; при наличии совместимой контрольной группы сравнивается PR-AUC активной модели.
8. `POST /models/{version}/activate` — активировать только прошедшую проверку модель. До публикации проверяется SHA-256 артефакта. В MySQL активация также обновляет реестр действующего MVP.
9. `POST /predict` или `POST /predictions/run-batch` — получить прогноз. `GET /predictions/{employee_id}` — история V2.

Синхронизация, приём событий увольнения и авторазметка **не запускаются автоматически из интерфейса или по расписанию**. Наличие полей даты/причины увольнения в Java не означает, что событие уже отправляется в V2.

## Снимок V2

```json
{
  "snapshots": [{
    "employee_id": "123",
    "snapshot_date": "2026-10-17",
    "features": {
      "department_code": "IT",
      "position_code": "DEV",
      "tenure_months": 14,
      "employment_rate": 1,
      "avg_workload_30d": null,
      "workload_days_available_30d": 0
    }
  }]
}
```

Схема признаков — `app/features.py`, входные схемы — `app/schemas.py`. Для одного сотрудника, даты и версии схемы хранится один снимок. Размеченный операционный снимок не перезаписывается. Будущие даты не допускаются. Отсутствующая нагрузка и нулевая фактическая нагрузка различаются в новых данных V2; старые нули Java автоматически восстановить невозможно.

В MySQL обе версии читают уровни риска из существующей `attrition_risk_thresholds`. Значения по умолчанию: LOW < 0,30; MEDIUM < 0,60; HIGH < 0,80; CRITICAL ≥ 0,80. Вероятности требуют калибровки на реальных данных перед практическим использованием процентов.

## Проверки

Локальное окружение из корня репозитория:

```powershell
python -m venv .venv-ml
.\.venv-ml\Scripts\python.exe -m pip install -r attrition-ml-service/requirements-dev.txt
$env:PYTHONPATH='attrition-ml-service'
.\.venv-ml\Scripts\python.exe -m pytest attrition-ml-service/tests -q
mvn -B test
```

Для отдельного тестового стенда:

```powershell
docker compose --env-file .env.example -p flowstaff-ml-check -f docker-compose.yml -f tools/compose.ml-acceptance.yml up -d --build
.\.venv-ml\Scripts\python.exe tools/verify-ml-integration.py
.\.venv-ml\Scripts\python.exe tools/verify-ml-fallback.py
```

Сквозной тест создаёт синтетические данные и активирует тестовую модель **только в изолированном стенде**: приложение `18080`, ML `18082`, MySQL `13307`. Основной проект на `8080` не используется.

Результаты проверки и приоритеты доработок: [отчёт об интеграции ML](../docs/ml-integration-report-2026-10-17.md).
